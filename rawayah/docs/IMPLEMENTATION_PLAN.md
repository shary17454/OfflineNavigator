# خطة التنفيذ — موروث

هذا المستند يربط طلب المستخدم الكامل (نظام إنتاجي متكامل عبر Flutter/Next.js/NestJS
بمعمارية Monorepo، ~50 جدول، لوحة إدارة، خط استيراد، بحث عربي، 2FA، خصوصية،
حقوق نشر، أداء، اختبارات، توثيق، Docker، CI) بالحالة الفعلية للمستودع، حسب
حالة كل بند وقت آخر تحديث لهذا الملف. يُحدَّث هذا الملف في نهاية كل مرحلة عمل
حقيقية — لا يُدَّعى فيه اكتمال أي بند لم يُختبر فعليًا.

آخر تحديث: بعد إتمام المرحلة 20 (إكمال الخيل/الإبل/الصقارة/كلاب الصيد/المكتبة/الوسائط + تحقق حي شامل على محاكي iOS بما فيه الحالات المصادَق عليها).

## قرار معماري مُتعمَّد: عدم إعادة هيكلة أدوات Monorepo

الطلب يحدد `pnpm` + `Turborepo` + `Melos` وبنية مجلدات معينة (`packages/`,
`packages-dart/`, `infra/`). المستودع الحالي يستخدم `npm workspaces` بنفس
البنية المنطقية (`apps/api`, `apps/web`, `apps/admin`, `apps/mobile`) وهو
**يعمل فعليًا ومختبر بالكامل** (38 اختبار حي). إعادة هيكلته إلى pnpm/Turborepo
الآن عملية عالية المخاطر منخفضة القيمة الوظيفية — ستُعرِّض كل العمل المُنجز
والمُختبر هذه الجلسة لخطر الكسر دون أي فائدة ملموسة للمستخدم. **لم يُنفَّذ هذا
القرار**؛ يبقى npm workspaces حتى يطلب المستخدم صراحة التبديل. كذلك لوحة
الإدارة (`apps/admin`) تبقى تطبيق Next.js منفصلاً بدل دمجها داخل `apps/web`
بمسارات محمية — نفس المبرر: تعمل وتُختبر، والدمج ليس له قيمة وظيفية تُذكر.

## المرحلة 10 (مكتملة) — نموذج القصيدة البنيوي

- `PoemVersion`, `PoemVerse` (أصبح مرتبطًا بالنسخة لا بالقصيدة مباشرة)،
  `PoemVerseVariant`, `PoemAttribution` — مخطط + هجرة حية مطبَّقة + API كامل
  محمي بصلاحية `content:edit` (حصرية لـOWNER) + 13 اختبارًا حيًا (ملف
  `test/poem-structure.spec.ts`) + تحقق حي فعلي عبر HTTP حقيقي (إنشاء نسخة →
  بيت → رواية بديلة → نسبة، ورفض المستخدم العادي بـ403).
- إصلاح جانبي أثناء نفس المرحلة: ثغرة كانت تسمح لأي مستخدم عادي بانتحال صفة
  "إجابة رسمية من المالك" على الأسئلة عبر إرسال `isOfficial:true` في الطلب
  مباشرة (`POST /questions/:id/answers`) — الخادم كان يثق بهذه القيمة من
  العميل دون أي تحقق. أُضيفت صلاحية `questions:answer_official` حصرية لـOWNER
  ويُحسب الحقل الآن من صلاحيات المستخدم الفعلية في قاعدة البيانات فقط، لا من
  مدخلات الطلب. تحقق حي: مستخدم عادي أرسل `isOfficial:true` فعاد `false`؛
  OWNER أرسل بلا الحقل إطلاقًا فعاد `true`.
- **درس تشغيلي مهم**: تعديل `prisma/seed.ts` وحده لا يكفي — يجب إعادة تشغيل
  `npm run seed` فعليًا ضد القاعدة الحية بعد أي تعديل عليه، وإلا بقيت
  الصلاحية الجديدة غير ممنوحة حتى لـOWNER (حدث هذا فعليًا أثناء التحقق الحي
  من هذه المرحلة وتم اكتشافه وإصلاحه فورًا).

## المرحلة 11 (مكتملة) — حذف الحساب وتصدير البيانات

- `POST /auth/account/delete` (بتأكيد كلمة المرور): حذف فعلي (لا Soft Delete
  وحده) لكل بيانات التفضيل/السلوك الشخصي (RefreshToken، Favorite، Follow،
  Notification، ReadingList، Rating، ContentReport، CommentReport، Profile)،
  ثم إخفاء هوية صف User نفسه (بريد وكلمة مرور عشوائيان غير قابلين للاستخدام،
  `status: DELETED`, `twoFactorSecret: null`) دون حذف الصف ذاته — لأن حذفه
  سيُسقط تلقائيًا (Cascade) أسئلة قد يكون عليها إجابات من مستخدمين آخرين،
  فيُتلف محتوى الآخرين. حساب OWNER يُمنع صراحة من حذف نفسه عبر هذا المسار.
- `GET /auth/account/export`: تصدير كل بيانات المستخدم الخاصة به (لا يشمل
  passwordHash إطلاقًا).
- 5 اختبارات حية (`test/account-deletion.spec.ts`) + تحقق حي فعلي عبر HTTP:
  تسجيل → تصدير → رفض حذف بكلمة مرور خاطئة (401) → حذف ناجح → فشل تسجيل
  الدخول بالبيانات القديمة (401) → تأكيد رفض OWNER لحذف نفسه (401).

## المرحلة 12 (مكتملة) — تكامل MinIO الفعلي لرفع الوسائط

- `docker-compose.yml`: خدمة `minio` جديدة (منفذ 9000 API + 9001 لوحة تحكم،
  healthcheck، Volume دائم)، وخدمة `api` تحصل الآن على متغيرات `S3_*`.
- `StorageService` (`shared/media/storage.service.ts`) أُعيدت كتابته بالكامل:
  عميل `@aws-sdk/client-s3` حقيقي متوافق مع S3 (`forcePathStyle: true` لازم
  لـMinIO)، إنشاء الحاوية تلقائيًا عند الإقلاع إن لم تكن موجودة، فحص إلزامي
  لنوع الملف الفعلي (mimetype لا الامتداد) وحجمه حسب الفئة (صورة/صوت/فيديو/
  مستند) قبل أي رفع، ورابط تنزيل موقَّع (Presigned URL) يُحسب عند كل قراءة
  بدل تخزينه دائمًا (15 دقيقة للملفات الخاصة، 24 ساعة للعامة) — لا رابط
  ثابت غير منتهي الصلاحية يُخزَّن في القاعدة إطلاقًا.
  - القديم كان يكتب الملفات مباشرة على القرص المحلي بلا أي فحص نوع أو حجم.
- `MediaService`/`MediaController`: يدعمان الآن `isPrimary` (وسم الملف
  الخاص)، ويُعيدان دائمًا رابطًا موقَّعًا طازجًا لا مسارًا محليًا.
- 6 اختبارات (`test/storage-validation.spec.ts`) لمنطق الفحص + تحقق حي كامل
  فعلي: رفع ملف mp3 حقيقي إلى MinIO حي عبر HTTP → استرجاع نفس محتواه عبر
  الرابط الموقَّع → رفض ملف `.exe` مُنتحل بامتداد صوتي (400).

## المرحلة 13 (مكتملة) — إصلاح وتوسيع CI

**تصحيح مهم لهذا الملف نفسه**: كان هذا المستند يدَّعي "❌ لا يوجد CI" — ادعاء
غير دقيق. ملف `.github/workflows/rawaya-ci.yml` موجود فعليًا منذ PR سابق
(#4) يسبق هذه الجلسة بالكامل. الخطأ صُحِّح فور اكتشافه أثناء هذه المرحلة.

الفجوة الحقيقية لم تكن "غياب CI" بل نقصه مقارنة بقائمة القسم 26، وتحديدًا:
- **خطوة `npm run lint` لم تكن تُستدعى إطلاقًا في CI أصلاً — وحتى لو استُدعيت
  كانت ستفشل فورًا**: Lint معطَّل بالكامل عبر المستودع الثلاثي (api/web/admin)
  بسبب خلل حقيقي في تحليل تبعيات npm workspaces — حزمة `eslint` لم تكن
  تُرفع (hoist) إلى `node_modules` الجذر رغم أن `eslint-plugin-react`
  المُرفوعة فعليًا تحتاجها هناك، فيفشل تحميلها بخطأ "Cannot find module
  eslint/package.json". أُصلح بإضافة `eslint` كـ devDependency صريح في
  `package.json` الجذر (سطر واحد يحل مشكلة الرفع). `apps/api` أيضًا لم يكن
  يملك ملف إعداد ESLint إطلاقًا (`eslint "src/**/*.ts"` بلا `.eslintrc`
  ينهار فورًا) — أُضيف `.eslintrc.js` قياسي (typescript-eslint) مع تعطيل
  `no-explicit-any` عمدًا (الكود الحالي يستخدم `any` على نطاق واسع لكائن
  المستخدم `@CurrentUser()`، وفرض القاعدة الآن سيُظهر مئات المخالفات غير
  المرتبطة بهذه المرحلة — قرار مُتعمَّد، ليس إغفالاً).
- بعد إصلاح آلية Lint نفسها، ظهرت مخالفات حقيقية: استخدام وسم `<a>` الخام
  بدل `<Link>` من Next.js للتنقّل الداخلي في 3 صفحات (`apps/web` الرئيسية
  و`apps/admin` الرئيسية) — تُصلح بطء التنقّل وتكسر الـPrefetching. أُصلحت
  جميعها. تبقّت تحذيرات غير حاجبة (`react-hooks/exhaustive-deps`) في 3 ملفات
  بلوحة الإدارة — موثَّقة كدين تقني، لم تُصلح لأنها خارج نطاق هذه المرحلة.
- أُضيف: **فحص الهجرات** الحقيقي (`prisma migrate deploy` ضد قاعدة بيانات
  فارغة داخل CI نفسه — لم يكن يُشغَّل، فقط `prisma generate`، وهذا لا يكشف
  انحراف الهجرات). تحقق يدوي إضافي هنا: طُبِّقت كلتا الهجرتين فعليًا ضد
  Postgres فارغ تمامًا في حاوية مؤقتة منفصلة — نجحتا بلا أي خطأ.
- أُضيف: **تدقيق أمني** (`npm audit`) — غير حاجب حاليًا (`|| true`) لأن
  المستودع يحمل فعليًا ٣٧–٤١ ثغرة معروفة في تبعيات فرعية (منها ١ حرجة و١١–١٤
  عالية) لم تُفحص بعد بندًا ببند؛ جعله حاجبًا الآن سيُفشل كل تشغيل CI فورًا.
  هذا دين أمني حقيقي غير مُصلَح، مذكور هنا صراحة لا مخفيًا.
- أُضيف: **فحص أسرار** (`gitleaks/gitleaks-action@v2`).
- أُضيف: **`flutter analyze`** لوظيفة Flutter (كان مفقودًا — يوجد `flutter
  test` و`flutter build` فقط).

**فجوة صادقة أخرى اكتُشفت أثناء هذه المرحلة**: `apps/web` و`apps/admin`
لا يملكان أي اختبار حقيقي إطلاقًا — سكربت `test` فيهما ينجح فقط بفضل علم
`--passWithNoTests`، وهذا يعني "لا اختبارات" لا "اختبارات ناجحة". غير
مُصلَح في هذه المرحلة (خارج نطاقها)، لكن يجب عدم الادعاء بوجود تغطية اختبار
للواجهات حتى تُكتب فعليًا.

## المرحلة 14 (مكتملة) — توسيع لوحة الإدارة: المصادر/الحقوق/العلاقات/الإعدادات

- وحدات خلفية جديدة كاملة: `sources` (CRUD لمصادر الاستشهاد بمستوى ثقة 1–5،
  تعطيل بدل حذف فعلي حفاظًا على سلامة الإحالات المرجعية)، `rights` (تسجيل/
  تحديث حالة حقوق أي محتوى عبر مفتاح مركّب contentType+contentId)، `settings`
  (مفتاح/قيمة عامة). العلاقات (`graph` module) كانت مبنية خلفيًا مسبقًا من
  مرحلة سابقة — أُضيفت لها واجهة إدارة فقط.
- 4 صفحات إدارة جديدة (`sources.tsx`, `rights.tsx`, `relations.tsx`,
  `settings.tsx`) مربوطة بالكامل بنفس نمط المصادقة المستخدم في الصفحات
  الموجودة (توكن OWNER من localStorage).
- **خطأ حي حرج اكتُشف وأُصلح أثناء التحقق**: `POST /settings` كان يفشل
  بخطأ 500 داخلي رغم صحة الطلب تمامًا. السبب: `ValidationPipe` العام في
  `main.ts` مُفعَّل بخيار `whitelist: true`، وهذا الخيار يحذف تلقائيًا أي
  حقل في جسم الطلب لا يحمل مُزخرِف class-validator واحد على الأقل — وحقل
  `value` في `UpsertSettingDto` (قيمة الإعداد، قد تكون أي نوع JSON) لم يكن
  يحمل أي مُزخرِف، فكان يُحذف بصمت قبل وصوله للخدمة، فتفشل Prisma لاحقًا
  بخطأ "Argument value is missing" — خطأ لا يمكن لاختبار Prisma مموَّه
  اكتشافه لأنه يقع في طبقة الـPipe قبل الخدمة بالكامل. أُصلح بإضافة
  `@IsDefined()` (يقبل أي نوع، يتحقق فقط من الوجود). أُضيف اختباران
  يُشغِّلان `ValidationPipe` الفعلي (لا مموَّه) للتأكد من عدم تكرار هذا

## المرحلة 17 (مكتملة) — ربط تسجيل الدخول/الحساب/السياسات + إصلاح خلل 2FA

**اكتشاف مهم أثناء المراجعة**: الموقع العام (`apps/web`) لم يكن يملك أي
صفحة تسجيل دخول أو تسجيل حساب إطلاقًا رغم أن كل الـAPI اللازم (تسجيل،
دخول، 2FA، حذف الحساب، التصدير) جاهز وموثَّق منذ مراحل سابقة — أي مستخدم
حقيقي لم يكن يقدر عمليًا يستخدم أيًّا من هذه الميزات من الموقع نفسه.

- `lib/http.ts`: أُضيف `post()` ومُدير توكن (`getToken`/`setToken`/
  `clearToken`) بمفتاح `rawaya_token` (نفس المفتاح المستخدم فعليًا من قبل

  OWNER)، `/register`، `/account` (عرض الملف الشخصي، تصدير البيانات كملف

  اختلاق بريد أو رقم تواصل وهمي).

  src/pages/login.tsx` لم يكن يتعامل مع استجابة `requires2FA` إطلاقًا —

  ثانية لإدخال رمز التحقق عند استلام `requires2FA`.
- تحقق حي كامل عبر HTTP حقيقي (لا نظري): تسجيل مستخدم جديد → `GET
  /users/me` (تحميل صفحة الحساب) → تصدير البيانات → رفض حذف بكلمة مرور
  قصيرة (400 تحقق) → رفض حذف بكلمة مرور خاطئة صحيحة الطول (401 حقيقي) →
  حذف ناجح. وتحقق منفصل لتدفّق OWNER الكامل (دخول → `requires2FA` →
  `2fa/verify` → accessToken) مطابقًا تمامًا لما ينفذه الكود الجديد.

## المرحلة 21: تصنيف الشعر متعدد الأبعاد، مكتبة الشاعر، العضويات المهنية، ووثائق السياسات

### أ. تصنيف الشعر — لماذا لم يُنفَّذ كقائمة واحدة

الطلب عدّد 25 نوعًا (فصيح، نبطي، محاورة، جاهلي، أموي، معلقات، غزل، رثاء،
خيل، عرضة...). تنفيذها كحقل واحد على القصيدة كان سيكون **خطأ نمذجة**، لأن
القصيدة الواحدة قد تكون نبطية + في الغزل + من منطقة + من عصر معيّن في آنٍ
واحد. لذلك فُصلت إلى أبعاد مستقلة في `PoetryTaxonomyDimension`:
`TRADITION` (نوع الشعر) و`ERA` (العصر) و`THEME` (الغرض) و`REGION` (المنطقة)
و`PERFORMANCE` (طريقة الأداء) و`COLLECTION` (مجموعات كالمعلقات).

- `PoetryTaxonomyTerm`: جدول لا enum — المالك يضيف ويعدّل ويرتّب ويخفي
  ويُنشئ تصنيفات فرعية (`parentId`) دون تعديل المخطط أو إصدار نسخة جديدة.
- `PoemTaxonomy`: علاقة متعدد-إلى-متعدد، فالقصيدة تحمل عدة أغراض معًا.
- **الدمج لا يحذف**: `mergedIntoId` يبقي التصنيف القديم مع إشارة إلى الهدف،
  وتُنقل قصائده تلقائيًا، ويُعاد توجيه تصفحه إلى الهدف — حتى لا تنكسر أي
  روابط أو مرجعيات خارجية.
- حماية من الحلقات في الشجرة: يُرفض جعل تصنيف أبًا لنفسه أو لأحد أصوله.
- **لا يوجد أي نوع شعر مكتوب في أي واجهة** — الشاشة تُبنى بالكامل من
  استجابة الخادم.

### ب. مكتبة الشاعر

`PoetFile` (واحدة لكل شاعر) + `PoetFileItem` بأنواع: نص، صوت، فيديو، صورة،
وثيقة، رابط خارجي. لكل مادة: المناسبة، التاريخ ودقته، الراوي/الملقي، المصور،
المصدر، مالك الحقوق، حالة الحقوق، الترخيص، من رفعها ومن راجعها ومن نشرها،
مستوى التوثيق، ملاحظات داخلية، والسماح بالعرض/التنزيل/الاستخدام التجاري.

التبويبات تُبنى من الخادم، و**التبويب الفارغ لا يُعاد إطلاقًا** — تنفيذًا
لشرط «لا تعرض تبويبًا فارغًا بلا حاجة» في مصدر البيانات لا في الواجهة.

توسيع `Poet`: الكنية، اللقب، دقة تاريخي الميلاد والوفاة (`DatePrecision`)،
ملاحظة اختلاف المصادر، وتاريخ آخر مراجعة. أسماء الشاعر البديلة تُخزَّن في
`NameVariant` الموجود، وعلاقاته بالشعراء والأماكن في `EntityRelation`
الموجود — إعادة استخدام لا تكرار.

**عرض التاريخ الظني**: الواجهة تعرض «نحو 1300» و«(مختلف فيه)» و«(غير مؤكد)»
بحسب `DatePrecision`، تنفيذًا لشرط عدم عرض معلومة غير موثقة كأنها حقيقة.

### ج. بوابة الحقوق — أهم حاجز قانوني في هذه المرحلة

لا يجوز نشر AUDIO/VIDEO/IMAGE/DOCUMENT ما لم تكن حالة الحقوق ضمن
(`PUBLIC_DOMAIN`, `LICENSED`, `PERMISSION_GRANTED`) **و** `allowDisplay=true`.
مفروض في `PoetryService.publishPoetFileItem` على مستوى الخادم لا الواجهة.

تحقق حي فعلي لكل الحالات: رفض النشر قبل الاعتماد، ورفضه مع حقوق `UNKNOWN`،
ورفضه مع `RESTRICTED`، ورفضه مع حقوق مسموحة لكن العرض ممنوع، ونجاحه فقط عند
اجتماع الشرطين. المساهم **لا يستطيع** ضبط الحقوق إطلاقًا — كل مادة تبدأ
`UNKNOWN` و`allowDisplay=false`، والحقوق بيد المالك عبر صلاحية `rights:manage`.

### د. العضويات المهنية والموافقة الصريحة

`ContributorApplication` بحالاته الثمانية (DRAFT → SUBMITTED → UNDER_REVIEW →
NEEDS_INFORMATION → APPROVED/REJECTED/SUSPENDED/REVOKED)، مع **فصل صريح** بين
حقول `public*` (تُعرض بعد القبول) وحقول `private*` (للتحقق فقط، لا تُعاد في
أي واجهة عامة إطلاقًا — مُثبَّت باختبار يفحص أن `select` لا يحتوي أي حقل
`private`).

`ConsentRecord` يحفظ **نص الموافقة كما عُرض وقت القبول** لا مجرد إشارة إليه،
مع إصدارها ونطاقها (`grantedScopes`) وتاريخها ووقت سحبها — حتى يمكن إثبات ما
وافق عليه المستخدم فعلًا لو تغيّر نص السياسة لاحقًا.

- `@Equals(true)` على خانتي الموافقة يرفض الطلب على مستوى الخادم — لا يكفي
  إخفاء الزر. مُثبَّت باختبار يستخدم `ValidationPipe` الحقيقي لا محاكاة.
- الواجهة لا تستخدم أي خانة محددة مسبقًا (`preChecked: false` صراحةً).
- **سحب الموافقة يوقف العضوية تلقائيًا** ويسحب الدور — لا يجوز إبقاء صفة
  عامة قائمة بلا موافقة سارية عليها.
- لا يُعتمد أي طلب بلا موافقة ظهور سارية (فحص إضافي في `reviewApplication`).

### هـ. صلاحيات الراوي والمؤرخ — الإضافة فقط

دورا `NARRATOR` و`HISTORIAN` يحملان صلاحيتين اثنتين فقط:
`poet_file:contribute` و`content:submit`. تحقق حي أثبت أن الراوي المعتمد:
- **يستطيع**: إضافة مادة، إرسالها للمراجعة، متابعة حالتها.
- **لا يستطيع** (403 من الخادم لكل حالة): النشر المباشر، اعتماد مادته،
  تغيير حقوقها، تعديل مادة مساهم آخر.
- مادته **لا تظهر للعامة** قبل نشر المالك (تحقق فعلي من الاستجابة العامة).

### و. وثائق السياسات

تسع وثائق (`PolicyDocument`) قابلة للتحرير من لوحة المالك: الشروط والأحكام
(17 بندًا تغطي البنود الـ16 المطلوبة + بند تواصل)، اتفاقية المساهم (12 إقرارًا
كما وردت حرفيًا)، الخصوصية، المحتوى، حقوق المؤلف، الإزالة، المصادر، الرواية
الشفهية، وإرشادات المجتمع.

- التحرير **يُنشئ إصدارًا جديدًا** بتاريخ سريان مستقل ولا يكتب فوق النص السابق.
- `PolicyAcceptance` + `ConsentRecord` يسجلان القبول بنص الوثيقة وإصدارها.
- الصياغة تستخدم «إلى الحد الذي تسمح به الأنظمة المعمول بها» ولا تدّعي إعفاءً
  مطلقًا، وتنص صراحةً على عدم استبعاد ما لا يجوز استبعاده نظامًا.

**تنبيه مكتوب داخل الوثيقة نفسها وفي `prisma/policies.ts`**: هذه مسودات
تشغيلية وليست استشارة قانونية، ولم يراجعها مختص قانوني مرخّص. بند النظام
المختص (16) مُعدّ مبدئيًا على أساس أن مقر المالك في المملكة العربية السعودية،
**ويجب اعتماده من محامٍ مرخّص قبل الإطلاق**، وكذلك عند التوسع لأي سوق خارجها.
هذا التزام بنص الطلب: «لا تخترع نصًا قانونيًا نهائيًا دون مراجعة مختص قانوني».

الموضوع ذو الرواية الواحدة لا يُعد اختلافًا فلا يظهر. ونص ثابت يوضح للقارئ
أن الروايات تُعرض دون ترجيح إحداها. تحقق حي بلقطة شاشة فعلية لروايتي نجد
والحجاز معًا.

`/poetry` (الأقسام بأبعادها) و`/poetry/[slug]` (قصائد القسم) و`/poets/[id]`
(مكتبة الشاعر بتبويباتها، بما فيها اختلاف الروايات وعرض دقة التواريخ).

صريح: «تنبيهات آلية (للمساعدة فقط — القرار لك)».

- **121 اختبارًا ناجحًا** في 20 مجموعة (كانت 113) — 8 اختبارات جديدة تغطي

## المرحلة 23: هوية بصرية موحّدة "المجلس" + وضع ليلي/نهاري كامل لتطبيق الجوال

طلب المستخدم: "الصفحات افخم من كذا... خلفيات وألوان تراثية من الطراز النجدي
عموم الصفحات بلا استثناء، وأيضًا كامل التطبيق يدعم الوضع الليلي والنهاري أو
حسب إعدادات الجهاز."

### الاختيار

عرضت 6 اتجاهات تصميم نجدية (الطين والشُرَف، باب نجد، المجلس، السدو، الجص،
واحة النخيل) كصفحة HTML واحدة بموك-أب هاتف حقيقي لكل اتجاه بالوضعين معًا،
واختار المستخدم **"المجلس"**: بنّي عميق كجدران المجلس، وذهب معدني، وخط فاصل
ذهبي رفيع يتلاشى عند طرفيه تحت كل عنوان — هادئ ومقروء، النص التراثي هو
البطل لا الزخرفة.

### نظام الثيم — `apps/mobile/lib/core/theme.dart`

أعيد بناؤه بالكامل حول `RawayaColors` (ThemeExtension) بحزمتين كاملتين
(نهاري/ليلي) بدل الثوابت المتفرقة السابقة (`kBrown`/`kGold`/`kCream`
كانت نهارية فقط ولا مقابل لها ليلًا — هذا بالضبط ما كان سيكسر الوضع الليلي
صامتًا). `context.rawaya` هو نقطة الوصول الوحيدة من أي شاشة.

مكوّنات هوية مشتركة: `RawayaGoldDivider` (الخط الذهبي المتلاشي)،
`RawayaSectionLabel` (عنوان القسم الفرعي الذهبي المصغّر)، ولوني دلالة
مضبوطين لكل وضع لا لونين ثابتين (`warning`, `danger`, `success`,
`warningSurface`).

### وضع السمة — `ThemeModeController`

`StateNotifier<ThemeMode>` بنفس نمط `AuthController` الموجود بالضبط
(نفس مبدأ الاتساق مع الكود القائم)، محفوظ في `SharedPreferences`، يُقرأ
عند إقلاع التطبيق. `MaterialApp.router` يُغذَّى بـ`theme`/`darkTheme`/
`themeMode` من `flutter_riverpod`. **الافتراضي `ThemeMode.system`** —
يتبع إعدادات الجهاز تلقائيًا كما طُلب صراحةً، مع خيار صريح للمستخدم
لتثبيت نهاري أو ليلي من صفحة الإعدادات (`RadioListTile` جديد).

### التطبيق على الشاشات — 45 ملفًا بلا استثناء

`SimpleListPage` و`DetailPage` (الإطاران العامّان اللذان تُبنى عليهما أغلب
شاشات القوائم والتفاصيل) أُعيد تصميمهما أولًا لأنهما يرفعان معظم التطبيق
تلقائيًا. ثم مسح شامل لكل استخدامات الألوان الثابتة:

- استبدال آلي آمن (سكربت Python) لـ`kCream`/`kGold`/`kBrown` بـ
  `context.rawaya.*` عبر 30 ملفًا — كل الاستخدامات كانت داخل نطاقات فيها
  `context` فعليًا (تحقق مسبق بالفحص اليدوي لكل استخدام قبل التشغيل).
- `home_page.dart` (الشاشة الرئيسية والقشرة العامة) أُعيد بناؤه يدويًا:
  إزالة الشريط العلوي البني الصلب لصالح عنوان مركزي على خلفية الصفحة
  يحدّه الخط الذهبي (اتساقًا مع بقية الشاشات)، والشريط السفلي بحدّ علوي
  وخلفية من الثيم بدل الألوان الافتراضية.
  الحدث الأمني للتلوين: `kBrown ← 0xFF2A1F14` لم يكن حتى نفس درجة
  `kBrown` العامة — الشاشة الرئيسية كانت تحمل لوحة ألوان مستقلة تمامًا
  عن بقية التطبيق قبل هذا الإصلاح.
- ألوان حرفية دلالية متبقية (`Color(0xFFFFF6E0)` لصناديق التنبيه،
  `Color(0xFF8D6E00)`/`Color(0xFF1B5E20)` لرؤوس الأقسام، `Colors.black54`
  للنصوص الثانوية، `Colors.red`/`Colors.green` لرسائل الخطأ/النجاح) عبر
  17 ملفًا إضافيًا — أُصلحت يدويًا بربطها بـ`context.rawaya.warning`/
  `.danger`/`.success`/`.textSecondary`/`.warningSurface` (لون جديد
  أُضيف للثيم بدل تكرار قيمة "كريمي فاتح" كانت ستختفي على خلفية ليلية).
- `offline_library_page.dart`: وضع القراءة الليلية اليدوي الموجود سابقًا
  (مستقل عمدًا عن ثيم التطبيق — يتيح قراءة ليلية بصرف النظر عن إعداد
  الجهاز، كتطبيقات القراءة المتخصصة) أُبقي كآلية لكنه يستخدم الآن نفس
  لوحة "المجلس" (`RawayaColors.light`/`.dark`) بدل قيم Hex منفصلة كانت
  ستُنتج مظهرًا غير متسق مع باقي التطبيق.

### خطأ متكرر واجهته الأداة الآلية وكيف اكتُشف

استبدال `kBrown` → `context.rawaya.textPrimary` داخل تعبيرات `const
TextStyle(...)` ينتج كودًا غير صحيح (استدعاء `context` ليس تعبيرًا ثابتًا
وقت الترجمة). النمط تكرر 60 مرة عبر الملفات. بدل إصلاح كل حالة يدويًا،
كُتبت أداة Python تفحص كل كلمة `const` في الملف، توازن الأقواس لإيجاد
نطاقها الفعلي، وتحذف كلمة `const` فقط إن كان `context.rawaya` داخل ذلك
النطاق تحديدًا — لا نطاقات أخرى غير متأثرة. شُغِّلت الأداة 3 مرات
(بعد كل دفعة استبدال جديدة كشفت عنها `flutter analyze`) حتى صفر أخطاء.
**الاعتماد على `flutter analyze` لا على القراءة اليدوية هو ما كشف كل
حالة** — 60 خطأ ترجمة كانت لتفوت لو اكتُفي بمراجعة العينة الأولى فقط.

### التحقق الحي

- `flutter analyze`: صفر أخطاء (بقيت تلميحات أسلوبية `prefer_const_constructors`
  غير معطِّلة، ودعوة تحذير قياسية من Flutter نفسه بخصوص `RadioListTile.groupValue`).
- `flutter test`: نجح بعد تحديث الاختبار الوحيد ليطابق نص شاشة البداية
  الجديدة (كان يبحث عن نص قديم حُذف عمدًا عند إعادة تصميم `SplashPage`).
- **تحقق حي فعلي بالتبديل بين الوضعين على مستوى نظام التشغيل** لا مجرد
  تخمين: `xcrun simctl ui <device> appearance light|dark` لتغيير مظهر
  المحاكي نفسه، مع `ThemeMode.system` (الافتراضي، بلا أي اختيار يدوي من
  المستخدم داخل التطبيق) — هذا يثبت أن "حسب إعدادات الجهاز" يعمل فعليًا
  لا افتراضًا نظريًا. لقطات فعلية لأربع شاشات (البداية، أقسام الشعر
  [نفس الشاشة التي اختار المستخدم تصميمها من الموك-أب]، الرئيسية، مكتبة
  الشاعر، الإعدادات) في كلا الوضعين — مطابقة بصريًا لتصميم "المجلس"
  المعتمد.
### إكمال التحقق المُقرّ بنقصه سابقًا

بدل انتظار عودة أداة المحاكي (بقيت متعطلة)، كُتب `test/theme_mode_test.dart`:
اختبار انحدار آلي دائم يثبت برمجيًا بالضبط ما تعذّر إثباته باللمس الحي —
ويبقى يحمي من أي كسر مستقبلي في `ThemeModeController`، بخلاف لقطة شاشة
تثبت لحظة واحدة فقط. أربع حالات:

1. الوضع الافتراضي (system) يتبع نظام التشغيل فعليًا.
2. تغيير نظام التشغيل مباشرة (بلا أي اختيار من المستخدم) يُطبَّق تلقائيًا.
3. **الاختيار اليدوي الصريح يتجاوز نظام تشغيل مضبوط على الوضع المعاكس** —
   يستدعي المسار البرمجي نفسه الذي يستدعيه `RadioListTile.onChanged` في
   `settings_page.dart` (`themeModeProvider.notifier.setMode(...)`)، ثم
   يؤكد أن الاختيار يبقى سائدًا حتى بعد "تغيّر" نظام التشغيل مجددًا لاحقًا.
4. الاختيار يُحفظ في `SharedPreferences` فعليًا ويُستعاد بعد إعادة تشغيل
   محاكاة (حاوية Riverpod جديدة تمثّل فتح التطبيق من جديد).

**خطأ اكتُشف أثناء كتابة الاختبار نفسه**: أول تشغيل بـ`tester.pump()`
مفردة بعد تغيير `platformBrightnessTestValue` فشل — الشجرة (Riverpod +
GoRouter) تحتاج أكثر من إطار واحد لتستقر بسبب جدولة إعادة البناء الداخلية.
تحقق مباشر بطباعة تصحيحية أثبت أن `MediaQuery`/`dispatcher` يتحدّثان فورًا
لكن `Theme.of(context)` يتأخر إطارًا واحدًا. هذا **فرق توقيت خاص ببيئة
الاختبار فقط** (إطارات التطبيق الفعلي تتوالى باستمرار دون خطوات يدوية)،
وليس خللًا حقيقيًا — أُصلح باستبدال `pump()` بـ`pumpAndSettle()` في نقاط
التغيير، لا بتغيير أي كود في التطبيق نفسه.

**النتيجة**: 5 اختبارات ناجحة إجمالاً في الملف الجديد + الأصلي،
`flutter analyze` صفر أخطاء، البناء ناجح. الفجوة التي أُقرّ بها في
المرحلة السابقة (عدم إثبات تجاوز الاختيار اليدوي لإعداد الجهاز) **مُغلَقة
الآن فعليًا**، ببرهان آلي متكرر لا لقطة شاشة واحدة.


## ترتيب التنفيذ التالي (يُحدَّث تباعًا)

1. توسيع تغطية اختبارات apps/web/apps/admin/apps/mobile تدريجيًا لبقية الصفحات.
2. (منفصلة، تحتاج نافذة اختبار مخصصة): ترقية NestJS 10→11 وNext.js 14→16
   لإغلاق بقية ثغرات npm audit ذات الخطورة العالية على التبعيات الإنتاجية.
3. مشغلات صوت/فيديو حقيقية (تحتاج حزمًا جديدة `audioplayers`/`video_player`
   ومحتوى وسائط حقيقي كافٍ للاختبار — لا يوجد سوى ملف اختباري واحد حاليًا).
4. استيراد بيانات تراثية حقيقية من مصادر خارجية (بانتظار تحديد المستخدم للمصدر) —
   يبقى هذا الأهم فعليًا لأن أغلب الشاشات الآن جاهزة تقنيًا لكن بمحتوى seed تجريبي لا تراث حقيقي موثَّق.

كل بند أعلاه يُنفَّذ بنمط: تصميم → قاعدة بيانات → API → صلاحيات → اختبارات
حقيقية → واجهة → تحديث هذا الملف. لا يُنتقل لبند تالٍ قبل اختبار السابق.
