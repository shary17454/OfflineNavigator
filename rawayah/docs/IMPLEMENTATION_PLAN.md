# خطة التنفيذ — موروث

هذا المستند يربط طلب المستخدم الكامل (نظام إنتاجي متكامل عبر Flutter/Next.js/NestJS
بمعمارية Monorepo، ~50 جدول، لوحة إدارة، خط استيراد، بحث عربي، 2FA، خصوصية،
حقوق نشر، أداء، اختبارات، توثيق، Docker، CI) بالحالة الفعلية للمستودع، حسب
حالة كل بند وقت آخر تحديث لهذا الملف. يُحدَّث هذا الملف في نهاية كل مرحلة عمل
حقيقية — لا يُدَّعى فيه اكتمال أي بند لم يُختبر فعليًا.

آخر تحديث: بعد إتمام المرحلة 14 (توسيع لوحة الإدارة: المصادر/الحقوق/العلاقات/الإعدادات).

## قرار معماري مُتعمَّد: عدم إعادة هيكلة أدوات Monorepo

الطلب يحدد `pnpm` + `Turborepo` + `Melos` وبنية مجلدات معينة (`packages/`,
`packages-dart/`, `infra/`). المستودع الحالي يستخدم `npm workspaces` بنفس
البنية المنطقية (`apps/api`, `apps/web`, `apps/admin`, `apps/mobile`) وهو
**يعمل فعليًا ومختبر بالكامل** (38 اختبار حي). إعادة هيكلته إلى pnpm/Turborepo
الآن عملية عالية المخاطر منخفضة القيمة الوظيفية — ستُعرِّض كل العمل المُنجز
والمُختبر هذه الجلسة لخطر الكسر دون أي فائدة ملموسة للمستخدم. **لم يُنفَّذ هذا
القرار**؛ يبقى npm workspaces حتى يطلب المستخدم صراحة التبديل. كذلك لوحة
الإدارة (`apps/admin`) تبقى تطبيق Next.js منفصلاً بدل دمجها داخل `apps/web`
بمسارات محمية — نفس المبرر: تعمل وتُختبر، والدمج ليس له قيمة وظيفية تُذكر.

## المرحلة 10 (مكتملة) — نموذج القصيدة البنيوي

- `PoemVersion`, `PoemVerse` (أصبح مرتبطًا بالنسخة لا بالقصيدة مباشرة)،
  `PoemVerseVariant`, `PoemAttribution` — مخطط + هجرة حية مطبَّقة + API كامل
  محمي بصلاحية `content:edit` (حصرية لـOWNER) + 13 اختبارًا حيًا (ملف
  `test/poem-structure.spec.ts`) + تحقق حي فعلي عبر HTTP حقيقي (إنشاء نسخة →
  بيت → رواية بديلة → نسبة، ورفض المستخدم العادي بـ403).
- إصلاح جانبي أثناء نفس المرحلة: ثغرة كانت تسمح لأي مستخدم عادي بانتحال صفة
  "إجابة رسمية من المالك" على الأسئلة عبر إرسال `isOfficial:true` في الطلب
  مباشرة (`POST /questions/:id/answers`) — الخادم كان يثق بهذه القيمة من
  العميل دون أي تحقق. أُضيفت صلاحية `questions:answer_official` حصرية لـOWNER
  ويُحسب الحقل الآن من صلاحيات المستخدم الفعلية في قاعدة البيانات فقط، لا من
  مدخلات الطلب. تحقق حي: مستخدم عادي أرسل `isOfficial:true` فعاد `false`؛
  OWNER أرسل بلا الحقل إطلاقًا فعاد `true`.
- **درس تشغيلي مهم**: تعديل `prisma/seed.ts` وحده لا يكفي — يجب إعادة تشغيل
  `npm run seed` فعليًا ضد القاعدة الحية بعد أي تعديل عليه، وإلا بقيت
  الصلاحية الجديدة غير ممنوحة حتى لـOWNER (حدث هذا فعليًا أثناء التحقق الحي
  من هذه المرحلة وتم اكتشافه وإصلاحه فورًا).

## المرحلة 11 (مكتملة) — حذف الحساب وتصدير البيانات

- `POST /auth/account/delete` (بتأكيد كلمة المرور): حذف فعلي (لا Soft Delete
  وحده) لكل بيانات التفضيل/السلوك الشخصي (RefreshToken، Favorite، Follow،
  Notification، ReadingList، Rating، ContentReport، CommentReport، Profile)،
  ثم إخفاء هوية صف User نفسه (بريد وكلمة مرور عشوائيان غير قابلين للاستخدام،
  `status: DELETED`, `twoFactorSecret: null`) دون حذف الصف ذاته — لأن حذفه
  سيُسقط تلقائيًا (Cascade) أسئلة قد يكون عليها إجابات من مستخدمين آخرين،
  فيُتلف محتوى الآخرين. حساب OWNER يُمنع صراحة من حذف نفسه عبر هذا المسار.
- `GET /auth/account/export`: تصدير كل بيانات المستخدم الخاصة به (لا يشمل
  passwordHash إطلاقًا).
- 5 اختبارات حية (`test/account-deletion.spec.ts`) + تحقق حي فعلي عبر HTTP:
  تسجيل → تصدير → رفض حذف بكلمة مرور خاطئة (401) → حذف ناجح → فشل تسجيل
  الدخول بالبيانات القديمة (401) → تأكيد رفض OWNER لحذف نفسه (401).

## المرحلة 12 (مكتملة) — تكامل MinIO الفعلي لرفع الوسائط

- `docker-compose.yml`: خدمة `minio` جديدة (منفذ 9000 API + 9001 لوحة تحكم،
  healthcheck، Volume دائم)، وخدمة `api` تحصل الآن على متغيرات `S3_*`.
- `StorageService` (`shared/media/storage.service.ts`) أُعيدت كتابته بالكامل:
  عميل `@aws-sdk/client-s3` حقيقي متوافق مع S3 (`forcePathStyle: true` لازم
  لـMinIO)، إنشاء الحاوية تلقائيًا عند الإقلاع إن لم تكن موجودة، فحص إلزامي
  لنوع الملف الفعلي (mimetype لا الامتداد) وحجمه حسب الفئة (صورة/صوت/فيديو/
  مستند) قبل أي رفع، ورابط تنزيل موقَّع (Presigned URL) يُحسب عند كل قراءة
  بدل تخزينه دائمًا (15 دقيقة للملفات الخاصة، 24 ساعة للعامة) — لا رابط
  ثابت غير منتهي الصلاحية يُخزَّن في القاعدة إطلاقًا.
  - القديم كان يكتب الملفات مباشرة على القرص المحلي بلا أي فحص نوع أو حجم.
- `MediaService`/`MediaController`: يدعمان الآن `isPrimary` (وسم الملف
  الخاص)، ويُعيدان دائمًا رابطًا موقَّعًا طازجًا لا مسارًا محليًا.
- 6 اختبارات (`test/storage-validation.spec.ts`) لمنطق الفحص + تحقق حي كامل
  فعلي: رفع ملف mp3 حقيقي إلى MinIO حي عبر HTTP → استرجاع نفس محتواه عبر
  الرابط الموقَّع → رفض ملف `.exe` مُنتحل بامتداد صوتي (400).

## المرحلة 13 (مكتملة) — إصلاح وتوسيع CI

**تصحيح مهم لهذا الملف نفسه**: كان هذا المستند يدَّعي "❌ لا يوجد CI" — ادعاء
غير دقيق. ملف `.github/workflows/rawaya-ci.yml` موجود فعليًا منذ PR سابق
(#4) يسبق هذه الجلسة بالكامل. الخطأ صُحِّح فور اكتشافه أثناء هذه المرحلة.

الفجوة الحقيقية لم تكن "غياب CI" بل نقصه مقارنة بقائمة القسم 26، وتحديدًا:
- **خطوة `npm run lint` لم تكن تُستدعى إطلاقًا في CI أصلاً — وحتى لو استُدعيت
  كانت ستفشل فورًا**: Lint معطَّل بالكامل عبر المستودع الثلاثي (api/web/admin)
  بسبب خلل حقيقي في تحليل تبعيات npm workspaces — حزمة `eslint` لم تكن
  تُرفع (hoist) إلى `node_modules` الجذر رغم أن `eslint-plugin-react`
  المُرفوعة فعليًا تحتاجها هناك، فيفشل تحميلها بخطأ "Cannot find module
  eslint/package.json". أُصلح بإضافة `eslint` كـ devDependency صريح في
  `package.json` الجذر (سطر واحد يحل مشكلة الرفع). `apps/api` أيضًا لم يكن
  يملك ملف إعداد ESLint إطلاقًا (`eslint "src/**/*.ts"` بلا `.eslintrc`
  ينهار فورًا) — أُضيف `.eslintrc.js` قياسي (typescript-eslint) مع تعطيل
  `no-explicit-any` عمدًا (الكود الحالي يستخدم `any` على نطاق واسع لكائن
  المستخدم `@CurrentUser()`، وفرض القاعدة الآن سيُظهر مئات المخالفات غير
  المرتبطة بهذه المرحلة — قرار مُتعمَّد، ليس إغفالاً).
- بعد إصلاح آلية Lint نفسها، ظهرت مخالفات حقيقية: استخدام وسم `<a>` الخام
  بدل `<Link>` من Next.js للتنقّل الداخلي في 3 صفحات (`apps/web` الرئيسية
  و`apps/admin` الرئيسية) — تُصلح بطء التنقّل وتكسر الـPrefetching. أُصلحت
  جميعها. تبقّت تحذيرات غير حاجبة (`react-hooks/exhaustive-deps`) في 3 ملفات
  بلوحة الإدارة — موثَّقة كدين تقني، لم تُصلح لأنها خارج نطاق هذه المرحلة.
- أُضيف: **فحص الهجرات** الحقيقي (`prisma migrate deploy` ضد قاعدة بيانات
  فارغة داخل CI نفسه — لم يكن يُشغَّل، فقط `prisma generate`، وهذا لا يكشف
  انحراف الهجرات). تحقق يدوي إضافي هنا: طُبِّقت كلتا الهجرتين فعليًا ضد
  Postgres فارغ تمامًا في حاوية مؤقتة منفصلة — نجحتا بلا أي خطأ.
- أُضيف: **تدقيق أمني** (`npm audit`) — غير حاجب حاليًا (`|| true`) لأن
  المستودع يحمل فعليًا ٣٧–٤١ ثغرة معروفة في تبعيات فرعية (منها ١ حرجة و١١–١٤
  عالية) لم تُفحص بعد بندًا ببند؛ جعله حاجبًا الآن سيُفشل كل تشغيل CI فورًا.
  هذا دين أمني حقيقي غير مُصلَح، مذكور هنا صراحة لا مخفيًا.
- أُضيف: **فحص أسرار** (`gitleaks/gitleaks-action@v2`).
- أُضيف: **`flutter analyze`** لوظيفة Flutter (كان مفقودًا — يوجد `flutter
  test` و`flutter build` فقط).

**فجوة صادقة أخرى اكتُشفت أثناء هذه المرحلة**: `apps/web` و`apps/admin`
لا يملكان أي اختبار حقيقي إطلاقًا — سكربت `test` فيهما ينجح فقط بفضل علم
`--passWithNoTests`، وهذا يعني "لا اختبارات" لا "اختبارات ناجحة". غير
مُصلَح في هذه المرحلة (خارج نطاقها)، لكن يجب عدم الادعاء بوجود تغطية اختبار
للواجهات حتى تُكتب فعليًا.

## المرحلة 14 (مكتملة) — توسيع لوحة الإدارة: المصادر/الحقوق/العلاقات/الإعدادات

- وحدات خلفية جديدة كاملة: `sources` (CRUD لمصادر الاستشهاد بمستوى ثقة 1–5،
  تعطيل بدل حذف فعلي حفاظًا على سلامة الإحالات المرجعية)، `rights` (تسجيل/
  تحديث حالة حقوق أي محتوى عبر مفتاح مركّب contentType+contentId)، `settings`
  (مفتاح/قيمة عامة). العلاقات (`graph` module) كانت مبنية خلفيًا مسبقًا من
  مرحلة سابقة — أُضيفت لها واجهة إدارة فقط.
- 4 صفحات إدارة جديدة (`sources.tsx`, `rights.tsx`, `relations.tsx`,
  `settings.tsx`) مربوطة بالكامل بنفس نمط المصادقة المستخدم في الصفحات
  الموجودة (توكن OWNER من localStorage).
- **خطأ حي حرج اكتُشف وأُصلح أثناء التحقق**: `POST /settings` كان يفشل
  بخطأ 500 داخلي رغم صحة الطلب تمامًا. السبب: `ValidationPipe` العام في
  `main.ts` مُفعَّل بخيار `whitelist: true`، وهذا الخيار يحذف تلقائيًا أي
  حقل في جسم الطلب لا يحمل مُزخرِف class-validator واحد على الأقل — وحقل
  `value` في `UpsertSettingDto` (قيمة الإعداد، قد تكون أي نوع JSON) لم يكن
  يحمل أي مُزخرِف، فكان يُحذف بصمت قبل وصوله للخدمة، فتفشل Prisma لاحقًا
  بخطأ "Argument value is missing" — خطأ لا يمكن لاختبار Prisma مموَّه
  اكتشافه لأنه يقع في طبقة الـPipe قبل الخدمة بالكامل. أُصلح بإضافة
  `@IsDefined()` (يقبل أي نوع، يتحقق فقط من الوجود). أُضيف اختباران
  يُشغِّلان `ValidationPipe` الفعلي (لا مموَّه) للتأكد من عدم تكرار هذا
  النوع من الأخطاء، بما فيها حالة الحافة `value: false` (قيمة منطقية خاطئة
  يسهل أن يحذفها كود ساذج يفحص "truthy" بالخطأ).
- 9 اختبارات جديدة (`test/sources-rights-settings.spec.ts`) + تحقق حي كامل
  لكل الوحدات الأربع عبر HTTP حقيقي: إنشاء مصدر (201) ورفض مستخدم عادي
  (403) وتعطيله، إنشاء/تحديث سجل حقوق بنفس المفتاح المركّب، إنشاء علاقة
  ومعاينتها متداخلة، وإعداد بقيمة نصية وأخرى منطقية false.
